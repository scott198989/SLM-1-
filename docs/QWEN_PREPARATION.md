An Ubuntu 24.04 x86-64 guest is a proposed choice, not an observed installation. Select and record a 64-bit CPython 3.12 interpreter; 3.12.14 is the candidate patch version already identified on the host, not a claim about the guest.

### Known correctness caveats

- bitsandbytes 0.49.2 fixed silently incorrect CUDA quantization/dequantization for noncontiguous inputs. Retaining 0.48.2 requires explicit input-layout checks on every relevant call path and regression evidence; if that cannot be established, evaluate a separately pinned fixed version. This finding does not prove the selected Qwen path is affected. [Official fix #1859](https://github.com/bitsandbytes-foundation/bitsandbytes/pull/1859).
- NVIDIA documents a compiler defect present since CUDA 12.8 in kernels with nested thread divergence, fixed in 13.2 Update 2. PyTorch 2.14.1's release notes identify that correction in its CUDA 13.2.2 Linux binaries. We have not established whether the exact torch/bitsandbytes binaries used here contain affected kernels. **Model-use certification remains blocked pending an upstream-supported disposition or a separately reviewed replacement stack.** Small arithmetic checks alone cannot clear this issue, and changing the installed Toolkit does not rebuild existing wheels. Do not silently change pins or assume every newer CUDA wheel contains the fix. [NVIDIA resolved issue](https://docs.nvidia.com/cuda/archive/13.2.2/cuda-toolkit-release-notes/index.html#cuda-compiler), [PyTorch release](https://github.com/pytorch/pytorch/releases/tag/v2.14.1).
- The bitsandbytes 0.48.2 tests document a CPU execution crash with Windows/torch 2.8.0. It does not establish a CUDA failure, but CPU offload is not an accepted fallback. [Tagged regression note](https://github.com/bitsandbytes-foundation/bitsandbytes/blob/0.48.2/tests/test_functional.py#L1355).

## Reversible installation and validation sequence — proposed only

1. **Select the OS and approve the narrow execution scope.** Record the actual interpreter, OS/WSL version, guest RAM and target-volume free space. If WSL is absent, its installation needs a separate system-change decision. Preserve current checkouts and managed Python. Create a new dedicated worktree/venv/cache only after environment setup is authorized; rollback removes only those newly created, identified paths, never originals or shared caches.
2. **Resolve before installing.** With package-network access explicitly authorized, request only prebuilt wheels from official PyTorch/PyPI sources, retain the exact seven pins, and capture a resolver dry-run/report for the chosen platform. Resolve torch against the official cu128 index and retain its exact wheel/hash; constrain that artifact during the remaining resolution. Capture every transitive version, wheel filename, origin and SHA-256 in a new platform lock before installation. Stop on a source-build fallback, conflict or missing wheel. A dry-run can still access/download package metadata and is not authorized today. [pip report/dry-run options](https://pip.pypa.io/en/stable/cli/pip_install/).
3. **Install the reviewed wheel set into that venv only.** After setup approval, verify installed versions against the lock, run dependency consistency/import checks, and record the Python executable and loaded library paths. Expect torch CUDA 12.8 and bitsandbytes' matching CUDA128 DLL on Windows or shared library on Linux; the loader selects by torch's CUDA version unless overridden. Record and reject unexplained overrides. Successful imports do not prove native kernels work. [Tagged bitsandbytes loader](https://github.com/bitsandbytes-foundation/bitsandbytes/blob/0.48.2/bitsandbytes/cextension.py).
4. **Run separately authorized synthetic GPU checks without Qwen weights or corpus data.** Verify device identity, capability 12.0, BF16 support, compiled architectures, actual CUDA library selection and free VRAM. Predefine numerical tolerances; exercise small FP32/BF16 matrix operations and synchronization, then a tiny NF4/double-quant linear forward/backward path. Compare finite outputs/gradients with an appropriate reference, inspect layouts, and fail on fallback or unsupported kernels. A tiny synthetic LoRA module can test the proposed paged AdamW optimizer, frozen base, adapter-only gradients/updates and save/reload. Authorization must explicitly include these synthetic backward/optimizer operations; it is not permission to train Qwen. Record failures and stop without changing driver/security settings or bypassing network restrictions.
5. **Restore the tokenizer prerequisites and verify the actual trainer boundary.** Obtain only the three exact assets in `manifests/qwen-tokenizer-assets.json` through an authorized, working route; the prior 403 is not to be retried or bypassed. Verify actual bytes against the manifest, then rerun the documented Qwen formatter tests and compare labels before/after the selected trainer's real collator on synthetic multi-turn/Unicode/padded examples. No model is needed. TRL's assistant-only masking requires generation tags absent from this original template, so retain the existing explicit labels rather than trusting the flag alone. [TRL 0.26.2 mask requirements](https://huggingface.co/docs/trl/v0.26.2/en/sft_trainer).

Stop here and report the evidence. Package and synthetic checks do not establish full-model fit, resolve the compiler caveat, release data or authorize weights/model loading. As of this research, the existing cloud CPU result remains **112 passing methods, five Qwen methods blocked by missing pinned assets (one class-setup error)**; the suite was not rerun for this documentation change. ## Model and memory gates after separate authorization

The [pinned Transformers 4.57.6 source](https://github.com/huggingface/transformers/blob/v4.57.6/src/transformers/models/qwen3_moe/modeling_qwen3_moe.py) uses attention `q_proj`, `k_proj`, `v_proj`, `o_proj` linears and unfused `ModuleList` experts with gate/up/down linears. Its source hash is retained in `manifests/qwen-runtime-source-evidence.json`. The proposed LoRA targets only those attention projections, rank 16, estimated 13,369,344 trainable parameters; router and experts stay frozen. Use NF4, double quantization, BF16 compute and explicit single-GPU placement. PEFT documents this quantized-base/adapter approach; Transformers reserves `device_map="auto"` for inference. [PEFT tagged guide](https://github.com/huggingface/peft/blob/v0.18.1/docs/source/developer_guides/quantization.md), [Transformers tagged guide](https://github.com/huggingface/transformers/blob/v4.57.6/docs/source/en/quantization/bitsandbytes.md).

**Adapter targets and quantization coverage are different.** The pinned converter recursively replaces eligible linears, including experts. After separately authorized loading, enumerate all 48 layers' 128 experts and their three projections: actual class, dtype, quantization state, device and stored bytes. Require four-bit expert storage, documented nonquantized exceptions elsewhere and no unexpected full-precision experts/CPU/disk placement. `load_in_4bit=True` alone is insufficient. Fused bare expert parameters would require a new audit: PEFT's experimental `target_parameters` concerns adaptation and does not establish quantization coverage. It is unnecessary for these attention targets. [Exact converter](https://github.com/huggingface/transformers/blob/v4.57.6/src/transformers/integrations/bitsandbytes.py), [PEFT parameter-targeting guide](https://github.com/huggingface/peft/blob/v0.18.1/docs/source/developer_guides/lora.md).

The [model card](https://huggingface.co/Qwen/Qwen3-30B-A3B-Base) specifies approximately 30.5B total versus 3.3B active parameters. All base weights still need storage; active parameters do not define model residency. BF16 arithmetic alone is about 61 GB decimal / 56.8 GiB, before loading overhead, so a full host BF16 copy would exceed a default 32 GiB WSL guest. A shard-wise/meta loading path needs measured host-RAM qualification, not an assumed fit.

The existing estimate is 14.2 GiB ideal four-bit storage, 16–19 GiB resident total and 20–29 GiB training peak at batch 1/context 2048. These are unmeasured; reported 32,607 MiB VRAM is about 31.84 GiB and desktop/driver use reduces availability. Retain the proposed 29 GiB rejection threshold and record torch allocated/reserved/peak memory, process/device-wide use where available, host/guest RAM and swap pressure separately. No silent offload or context increase. Budget disk for pinned model shards, package/cache copies, WSL disk growth, logs and checkpoints; the reported 1.14 TB free is capacity evidence, not a verified download-size or free-space guarantee on every volume.

Before any Qwen download/load, separately approve that action, clear the runtime correctness caveats and pin the exact revision's shard manifest/hashes. Before a Qwen optimizer step or 20-step memory pilot, separately authorize it and complete data, family, rights, baseline and development gates. The proposed pilot then discards its adapter and resets seed/data order; checkpoint reload must preserve labels and outputs, and a resumable run must capture optimizer/scheduler/RNG/data position as well as adapter state.

Freeze dataset/family/tokenizer/runtime/template/render hashes, seeds, decoder, tools and RAG index. Use the [paired evaluation protocol](PHASE3_BASELINE_EXPERIMENT.md); select checkpoints with independent development families, never sealed gold. Current development count is zero; the 16-example calculator pilot is integration data and the 12 sealed statistics tasks are a one-family diagnostic.
